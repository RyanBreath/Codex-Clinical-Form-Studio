# 附件與 CBCT 服務整合：實作前契約

日期：2026-10-28。狀態：規劃；附件傳輸與跨系統授權尚未實作或驗收。延續 ADR 0011、0012，不改變院端預設保管已簽 ICF 的決策。

## 已查證的既有能力

唯讀參考相鄰專案「他院CBCT 上傳機制」的 `docs/api/API契約.md`、`UploadSessionsController.cs` 及 API `Program.cs`：

- 已有 DICOM、PDF、JPEG、PNG、HEIC、EDF 類型與 Project 允許類型控制；普通文件不必偽裝成 DICOM。
- 上傳已有 manifest、短效上傳網址、檔案確認、完成及查詢驗證結果；檔案摘要有 SHA-256、預期大小、惡意程式與內容驗證狀態。
- 授權依 Project、Organization、Site 與人員指派解析；不能只拿表單平台的研究 ID 宣稱有檔案權限。
- 目前 API 採 Cookie／OIDC BFF；未找到 AddJwtBearer。不能假設平台服務帳號的 Bearer token 已可直接呼叫。

上述是原始碼與契約查核，沒有修改該專案，也沒有在既有服務建立測試上傳或取得真實資料。

## 責任邊界

表單平台保存附件的研究關聯、分類、用途、版本與操作稽核；既有上傳服務負責私有儲存、上傳工作階段、內容／惡意程式檢核及檔案生命周期。以適配器整合，避免複製第二套上傳與掃描引擎。

平台新增 Attachment metadata 時至少需要：內部附件 ID、Study／Site／Subject、可選 Visit／Response／CollectionBasis、category、sourceSystem、外部 Upload／File ID、原檔顯示名稱、媒體類型、大小、SHA-256、驗證狀態與查核時間。不得保存任意用戶提供的永久網址、S3 key 或外部「檢核通過」宣告作為授權依據。

研究與外部 Project、院所與外部 Site 的對應須由授權管理員配置及稽核；不能靠相同代碼自動匹配。缺少對應、失效或資料矛盾均不放行。

## 受控流程

1. 平台檢查操作者、研究院所範圍、附件分類、用途及保管政策，再建立本地 upload intent。
2. 適配器以外部服務接受的可信身分要求工作階段；使用外部服務回傳的短效網址。後端應限制設定的服務位置，不接受請求任意指定主機。
3. 上傳完成只代表已收件。平台向外部服務查核檔案 ID、Project／Site、雜湊、大小與實際檢核結果。
4. 未完成或無法確認檢核時留在 pending／quarantined，不可下載；檢核失敗則 blocked。只有符合政策的最終結果可轉 ready。
5. 下載每次重新檢查平台與外部授權，取得短效存取或受控串流；不把永久連結交給瀏覽器。
6. 外部事件與輪詢均須冪等，保存事件 ID／來源修訂並對帳；事件不明或順序顛倒時先查回權威狀態。

## ICF 的特別規則

- 院端保管：平台只登錄文件參考及確認證據，不因此複製已簽 ICF。切換集中保管不能回溯推定授權搬移文件。
- 集中保管：已簽 ICF 使用獨立的文件讀取權限，不能因具有一般研究資料 Read／Export 就下載。
- 同意證據的收件可能發生在收集依據確認前，必須有專用目的與權限；一般研究附件仍通過研究收集依據關卡。
- 已簽文件不是可編輯的 ICF 範本。更正以新版本或補充文件處理，保留原本證據。
- 收件與檢核完成不等於有效同意，仍由授權人確認版本、簽署及適用範圍。

## 下一批實作與驗收

先在本專案建立附件 metadata、政策控制、適配器界面與合成契約測試。跨系統認證需與既有上傳服務協作：正式決定受限服務帳號／受託人機制、audience／scope、來源綁定與撤銷；不轉存使用者 Cookie，不拿開發標頭代替正式整合。

接著在隔離測試環境完成 PDF／照片傳輸、掃描失敗隔離、院所錯配、重送去重、授權撤銷後拒絕下載、ICF 權限分離與備份復原。一般附件通過後再驗證 DICOM／CBCT。正式服務串接尚未完成前，介面不得顯示「已整合」或「已通過掃描」。
