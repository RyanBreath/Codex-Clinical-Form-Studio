# 架構與資料控制

## 實作配置

- `backend/FormPlatform.Api/`：ASP.NET Core API、EF Core／PostgreSQL、研究與院所授權、表單版本、收集依據及填答狀態。
- `template/crf/src/platform/`：研究工作入口及視覺化編輯器。
- `template/crf/src/FormRenderer.tsx`：共用 renderer，區分 demo、平台填寫及設計預覽；平台模式不自動下載資料或提供任意 API URL 傳送。
- `template/data-dictionaries/crf-contract.meta-schema.json`：前後端共用結構規格，後端嵌入同一份資源。
- `tests/FormPlatform.IntegrationTests/`：實際 PostgreSQL 的多院、發布與填答流程測試。

## 重要控制

研究權限來自資料庫指派，開發身分標頭或外部登入本身不賦予研究權限。院端以研究與院所限定範圍；跨院需明確指派。已簽 ICF 文件權限與一般資料讀取分開。

表單與新建 ICF 文件的正式發布均由設計參與人以外的授權人核准，固定內容雜湊。ICF 草稿不對一般收集人員顯示，也不能登錄為適用收集版本；已核准文件不可編輯，停用後阻擋依賴它的新收集。正式填答關聯固定表單版本；計算欄位由後端重新計算，不能信任用戶端傳入的結果。

變更操作以 Serializable 資料庫交易執行；填答採預期修訂號檢查。稽核及修訂紀錄由應用程式限制為新增，業務異動與待送事件於同一交易儲存。事件派送與正式稽核防竄改部署尚需後續實作／驗收。

契約 1.2 允許明確的 unresolved 對應狀態；必要欄位仍由研究政策在送審、發布與採用／新收集時檢查。既有 1.0／1.1 契約保留原有行為。

## 受控整合與匯出

整合程式的來源綁定於帳號，須同時具備院所範圍的整合與收集權限。外部寫入與瀏覽器共用後端收集驗證；以 Idempotency-Key 加請求雜湊保存去重收據，相同識別配不同內容會衝突。外部代碼與來源寫入修訂紀錄，不能藉一般入口繞過來源控制。

匯出保存固定修訂資料、表單版本與內容雜湊；下載限原申請人，重新檢查授權及適用依據。目前是同步 JSON 快照，尚未提供大量工作佇列。

版本編號須與契約 schemaVersion 一致，契約識別碼以 formId/schemaVersion 結尾；同範本另建版本不可沿用前版識別碼。既有版本識別碼不可更換，正式發布內容仍不可修改。

## 限制

正式環境 OIDC／MFA 與維運、實際 CTMS 跨站登入、CBCT／一般附件、對外事件派送及上線驗收等尚未全部完成。已有本機資料庫備份還原演練，尚未涵蓋附件、IdP 與正式環境金鑰。現況不代表可直接收真實資料，不宣稱臨床或法規合規認證。
